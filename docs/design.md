# Design

## Two problems, not one

"Turn this into ASCII art" collapses two different problems that have
different difficulty and different correct methods.

**Image to ASCII** is deterministic rendering: a function from a bitmap and a
target grid size to a grid of characters. There is no ambiguity about what
"correct" means beyond a choice of perceptual objective, and no learned model
is required to do the mapping. Three tiers, increasing in how much local
image structure they use:

1. **Luminance ramp.** Downsample the image to a `cols x rows` grid, average
   luminance per cell, map to a character from a ramp ordered by measured ink
   coverage (not the visually-ordered ramps copied around online, which are
   wrong for most monospace fonts — see "measured glyph coverage" below).
2. **Structure-aware glyph matching**, following Xu et al.'s approach to
   structure-based ASCII art generation: for each cell, compare local
   gradient/edge structure against a library of glyph bitmaps rendered in the
   target font, and pick the glyph whose rendered shape best matches the
   cell's structure, not just its average brightness.
3. **Edge-directed.** Run a Sobel filter, take the gradient angle per cell,
   quantize it to one of `| / - \`, and use edge glyphs on high-gradient
   cells with a luminance or structure fallback elsewhere. Produces cleaner
   line art on images with strong edges (logos, line drawings) than either
   tier above.

### Measured glyph coverage

A luminance ramp needs each candidate glyph's actual ink coverage, in the
rendering font, not a guessed visual ordering. Coverage is computed once per
font by rasterizing every candidate glyph at the target cell size and
measuring the fraction of dark pixels:

```
coverage(g) = (# dark pixels in rasterize(g, font, cell_size)) / (cell_size.w * cell_size.h)
```

Glyphs are sorted by `coverage(g)` to build the ramp. This makes the ramp
correct for whatever font is actually used to view the output, instead of
assuming the classic `" .:-=+*#%@"` ordering, which was measured (informally)
for one specific font and breaks for others.

`asciiart/render.py` exposes:

```python
render(img, cols, mode="luminance" | "structure" | "edge") -> str
rasterize(ascii_text, font) -> Image
```

`rasterize` is the inverse direction — turn ASCII text back into a bitmap in
a given font — and is the shared primitive the verifier and the CLI both
use. CLI: `python -m asciiart.cli`.

## Prompt to ASCII by an LLM is a different, much harder problem

Asking an LLM to autoregressively emit an `80x24` grid of characters that
looks like a target image or concept runs into problems that are structural,
not a matter of scale or fine-tuning:

- **BPE destroys the grid.** Byte-pair encoding merges whitespace runs and
  common character sequences into single tokens with no awareness of column
  position. The same visual column boundary lands at a different token
  boundary on every row, so the model cannot maintain a consistent notion of
  "column 40" the way a vision or grid model would.
- **No 2D receptive field.** A causal transformer attends over a flattened
  1D token sequence. Two cells that are vertically adjacent in the rendered
  grid (row `n`, row `n+1`, same column) are separated by roughly one row's
  worth of tokens in the sequence, and nothing in the architecture privileges
  that relationship over any other pair of equally-distant tokens.
- **Autoregressive order is wrong for a raster.** Left-to-right, top-to-bottom
  generation commits to early rows before the model has "seen" what the
  bottom of the image needs to look like, unlike a renderer or a diffusion
  process that can iterate on the whole grid at once.
- **No differentiable or checkable reward existed.** Without a way to score
  a generated grid against a target, there was nothing to train against
  beyond imitating existing outputs.

The consequence: existing SFT corpora for this task (e.g. the ~140k-example
HF ASCII-art dataset) are prompt/ASCII pairs generated by running images
through `ascii-image-converter` and captioning them. A model trained on that
corpus learns to imitate `ascii-image-converter`'s output distribution, not
to solve image-to-ASCII from first principles — and it inherits every
artifact and failure mode of that specific converter.

**Correct decomposition:** prompt to generative image model (already solved,
already good) to structure-based converter (problem 1, already deterministic
and correct) to ASCII. There is no reason to ask an LLM to do the whole
pipeline in one autoregressive pass when the middle step already has a
correct closed-form answer.

## What's actually worth building

The reason problem 2 is not simply "unsolved and therefore skip it": ASCII
grids have a property most open-ended generation tasks lack — the
constraints are checkable predicates. Fixed width. Fixed charset. A target
image to rasterize-and-compare against. That checkability is what makes the
following worth building, in order of how directly it uses the checkability:

### (a) Constrained decoding

Width and charset constraints (each row exactly `cols` characters, only
glyphs from the target font's charset) can be enforced structurally at
decode time — mask logits for any token that would violate line length or
introduce a disallowed character — rather than hoped for via prompting. This
does not fix the deeper 2D/ordering problems above, but it removes a class
of trivial failures (ragged grids, wrong glyphs) that would otherwise
dominate error analysis.

### (b) RLVR with a real verifier

`asciiart/verify.py` implements the verifier: rasterize the generated ASCII
text in the target font (reusing `rasterize` from `render.py`), then score
against the target image with two terms.

**SSIM term**, computed per cell (not globally) and averaged:

```
SSIM(x, y) = ((2*mu_x*mu_y + c1) * (2*sigma_xy + c2)) /
             ((mu_x^2 + mu_y^2 + c1) * (sigma_x^2 + sigma_y^2 + c2))
```

applied to each rasterized-glyph cell against the corresponding patch of the
target image (`mu`, `sigma`, `sigma_xy` computed over the cell's pixels;
`c1 = (0.01*L)^2`, `c2 = (0.03*L)^2` with `L` the dynamic range), then
averaged over all cells to give a single scalar in `[-1, 1]`.

**Edge-alignment term**: Sobel edges on both the target image and the
rasterized ASCII output, then an edge-F1 (precision/recall on edge pixels
within a small tolerance radius) between the two edge maps.

```
reward = w_ssim * SSIM + w_edge * edge_F1
```

The edge term exists specifically to close a reward hack: SSIM alone rewards
a uniform mid-gray fill (e.g. an even scatter of `.` or `:`) on any image
whose average luminance is mid-range, because per-cell SSIM against a
locally-smooth patch is high for a locally-uniform glyph even when it
carries no structure. An output with no edges at all scores near zero on
edge-F1 regardless of its SSIM, so the combined reward cannot be maximized
by degenerate uniform fills. This is a specific instance of the general
principle that a verifier's normalization has to differ from the reward it's
supposed to check — if both terms could be maximized by the same
degenerate output, the second term isn't actually protecting anything.

### (c) Direct discrete search as a non-neural upper baseline

`asciiart/anneal.py`: simulated annealing directly on the `80x24` character
grid, using the verifier's reward as the energy function. No neural network
involved — this establishes what the best achievable score is when the only
constraint is compute, so that later RLVR results can be read against a real
ceiling instead of an arbitrary target.

**Move set:**
- single-cell substitution (replace one glyph with another from the charset)
- row shift (shift a contiguous run of cells left/right by one, refilling
  the gap)
- block swap (swap two cells, useful for correcting locally-transposed
  structure without destroying overall density)

**Schedule:** standard geometric cooling, `T_{k+1} = alpha * T_k` with
`alpha` around 0.995, starting `T_0` set so the initial acceptance rate for
energy-increasing moves is roughly 0.3–0.5 (calibrated per image by a short
burn-in), terminating after a fixed move budget or when acceptance rate
drops below a floor for a sustained window.

### Reward-hacking risks and mitigations

| Risk | Mitigation |
|---|---|
| Uniform mid-density fill maximizes SSIM on mid-luminance images | edge-F1 term (see above) |
| Degenerate charset collapse (model always emits the single highest-average-SSIM glyph) | charset-entropy penalty as a secondary term during RLVR; monitored, not necessarily always active |
| Verifier exploited via off-target font metrics (model learns kerning quirks of the rasterizer rather than general structure) | evaluate against more than one monospace font at test time; a policy that only works against the training-time font's rasterizer is treated as overfit to the verifier, not solved |
| Reward saturates on trivial/blank images, masking regressions on hard images | fixed 50-image evaluation set with a stratified difficulty spread (see below), reported per-stratum, not just as one aggregate mean |

## Evaluation protocol

A fixed synthetic set of 50 images, generated once and reused across every
phase so numbers are comparable run over run. Stratified across:

- flat/simple shapes (logos, icons) — tests whether structure-aware modes
  beat luminance-only
- photographs with strong edges — tests the edge-alignment term
- photographs with low edge content / smooth gradients — the case most prone
  to the uniform-fill reward hack
- text/line-art — tests glyph matching against the structure-aware converter

For each image, report SSIM and edge-F1 against `asciiart/render.py`'s
`mode="structure"` output as the reference (not against the raw image
directly — the reference is what the deterministic converter can achieve,
since that's the ceiling any prompt-driven method should be judged against),
plus the same two metrics against the simulated-annealing baseline's output
as a compute-unbounded ceiling. A model or constrained-decoding scheme is
reported as three numbers per image: SSIM, edge-F1, and constraint
violations (ragged rows, out-of-charset glyphs) — not collapsed into a
single leaderboard score, since the failure modes above have different
practical consequences and shouldn't be averaged away.
